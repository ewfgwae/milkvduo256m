★ 安全铁律 (三条, 每次动手前先过一遍)
  1) fip.bin 是唯一的引导固件, 不要随手动它。本板有 SD 读卡器, 最坏情况可以重写整卡
     救回来, 但要拆机取卡、代价高。
  2) 改小核固件一律走"热更"(见 2026.9.28-小核-帧率修复与热更.txt 第五章) ——
     它不碰 fip.bin、不重启系统。
  3) 改内核/重编内核时: /mnt/system/ko 下的 .ko 必须用**同一棵内核树**一起重编,
     否则会出现"模块能加载但功能静默失效"甚至内核 Oops
     (实例见 2026.9.30-摄像头-无法出图.txt 第六章)。

【本文件背景】
  目标: 把摄像头画面"取中间"显示到 ST7789 屏上, 用 LVGL 显示, 并取消
        "没有画面时默认的红屏"。
  结论: **做到一半, 卡在编译环境 ABI 不匹配上**。本文件把已经查清的东西、

================================================================================
  一、目标与架构 (已确定)
================================================================================

1.1 数据流
--------------------------------------------------------------------------------
  1) 摄像头 GC2083 (1920x1080)
  2) -> VI 采集
  3) -> VPSS 硬件缩放到 240x240 (16:9 画面自动取中间)
  4) -> 大核 CVI_VPSS_GetChnFrame 抓帧 (NV21)
  5) -> 大核做 NV21 -> RGB565(大端) 转换 (硬件不做这一步)
  6) -> 写进共享内存 LCD_SHM_PHYS 的 fb 区
  7) -> mailbox 发 LCD_CMD_CAM
  8) -> 小核 LVGL 用 image 控件显示到 ST7789

1.2 为什么必须"大核取画面 + 小核显示"
--------------------------------------------------------------------------------
  1) 屏幕**完全由小核(C906L)独占**: lvgl_task.c 是屏的唯一所有者, 直接用 SPI2
     寄存器 + sysDMA 送显, 不经过 Linux 的 spidev, 也不经过 Linux GPIO 子系统。
  2) 大核(Linux)根本碰不到那根 SPI2 数据通路(它只做 CPU 监控并走 mailbox 送数)。
  3) 所以大核只能把像素放进共享内存, 由小核搬到屏上 —— 这也是本工程既有的
     "lcd_sender 填色/彩条" 那套机制的延伸。

1.3 屏幕方向与"取中间"的换算 (重要)
--------------------------------------------------------------------------------
  1) 屏是 **240x320 竖屏**; 摄像头出图是 320x240 横屏。
  2) 用户要求"截取中间的 320x240 显示到屏幕上"。已定的做法:
       a) 摄像头侧取中间的 **240x240** 正方形 (VPSS 硬件缩放自动居中);
       b) 屏 320 高、图 240 高 => 上下各留 40 像素黑边, 图竖直居中;
       c) 这样不变形、不旋转。如果以后要"铺满 240x320", 需要旋转 90 度:
          小核 LVGL 做 image 旋转最省事; 大核用 napajs/软件旋转会耗 CPU。
  3) 相关宏: LCD_W=240 / LCD_H=320 (lcd_shm.h); CAM_W=CAM_H=240 (工具里)。

2.1 大核工具 tools/cam_lcd.c (源码已在仓库)
--------------------------------------------------------------------------------
  1) 功能: 初始化 VI+VPSS -> 抓 240x240 帧 -> NV21 转 RGB565 -> 塞共享内存
     -> 发 LCD_CMD_CAM。
  2) 支持 `--dump out.ppm` 只抓一帧存图(验证抓帧通路, 不碰屏);
     `--frames N` 送 N 帧后退出。
  3) 关键实现点(都验证过):
       a) pixel format 是 **NV21**(VI_PIXEL_FORMAT = PIXEL_FORMAT_NV21),
          UV 平面上 **V 在前 U 在后**; 按 NV12 写会得到错误颜色。
       b) RGB565 必须**大端**写(高字节在前), 与 ST7789 及小核 lv_conf.h 的
          LV_COLOR_16_SWAP=1 约定一致。
       c) 抓帧有行 stride(f->u32Stride[]), 不能假设 width*bytes 连续。
  4) 交叉编译命令(用板上的库链接时):
       GCC=/home/chen/duo-sdk-v2/host-tools/gcc/gcc-linaro-7.3.1-2018.05-x86_64_aarch64-linux-gnu/bin/aarch64-linux-gnu-gcc
       CFLAGS="-march=armv8-a -O2 -DNDEBUG -DCV181X -D__CV181X__ -std=gnu11 -fsigned-char"
       CFLAGS="$CFLAGS -I<include/system> -I<include/tdl> -I."
       LDFLAGS="-L<libs> -lini -lsns_full -lsample -lisp -lvdec -lvenc -lawb -lae -laf \
                -lcvi_bin -lcvi_bin_isp -lmisc -lisp_algo -lsys -lvi -lvo -lvpss -lrgn -lgdc \
                -lpthread -lrt -latomic -lm"
       $GCC $CFLAGS -o cam_lcd cam_lcd.c $LDFLAGS
     ★ 少了 -lrt 会报 timer_create/timer_settime 未定义; 少了 -lm 会报 sincos/powf。

2.2 新的 mailbox 命令 LCD_CMD_CAM (已定义)
--------------------------------------------------------------------------------
  1) 在 lcd_shm.h 里新增:
       #define LCD_CMD_CAM  0x48
     语义: 大核已把一张 RGB565(大端) 图写进 fb 区, 矩形在 ctrl 的 x0/y0/x1/y1;
           小核用 LVGL 把它显示出来, 并**停掉跑分 demo**(进入"画面模式")。
  2) 两份副本已同步(内容逐字节一致):
       src/big_core/lcd_shm.h
       src/sdk_overlay/freertos/cvitek/task/comm/src/riscv64/lcd_shm.h

2.3 抓帧 API 已确认可用
--------------------------------------------------------------------------------
  1) CVI_VPSS_GetChnFrame(grp, chn, &frame, timeout_ms) / ReleaseChnFrame 都在
     板上的 libvpss.so 里(符号齐全, 含 SetChnAttr / EnableChn / SetChnCrop)。
  2) VPSS 通道属性设 240x240 即可让硬件缩放, 比例不同时默认取中间。
  3) 板上**没有** VGS 库(libvgs.so 不存在), 所以旋转/缩放只能靠 VPSS 或 CPU。

3.1 现象
--------------------------------------------------------------------------------
  1) cam_lcd 能跑、能打印, 走到 VI 初始化处:
       [1] sizeof(SAMPLE_INI_CFG_S)=232 sizeof(SAMPLE_VI_CONFIG_S)=788
       [2] ParseIni OK, enSnsType[0]=26 devNum=1
       [3] GetSensorInfo OK
       [4] IniToViCfg ret=0 workingViNum=0      <- 应该是 1 却是 0
       [5] GetSizeBySensor ret=0
       Segmentation fault                        <- 随后访问空数组就崩
  2) workingViNum=0 说明库函数没按我给的布局写这两个字段。

3.2 定位手段(tools/abi_probe.c, 已写)
--------------------------------------------------------------------------------
  1) 做法: 把 SAMPLE_VI_CONFIG_S 整块填 0xAA, 调库里现成的
     SAMPLE_COMM_VI_IniToViCfg(), 再看哪些字节被写了、写成了什么。
     这样能**反推库真正使用的结构布局**, 不靠猜。
  2) 实测输出(关键):
       sizeof(SAMPLE_VI_INFO_S) = 152      <- 头文件认为的
       库写第一组字段在 off 0..~33、第二组从 off 132 开始
       => **库认为 SAMPLE_VI_INFO_S = 132 字节, 头文件认为是 152 字节, 差 20**
     20 字节 / 每个实例 * VI_MAX_DEV_NUM(5) 累积, 于是 s32WorkingViNum 完全错位。
  3) 结论: 只要头与库不配套, 这类结构体传参的函数全都不可信。

3.8 ★ 方案3(RTSP 拉流)的进展与新卡点 —— 2026-09-30 收尾
--------------------------------------------------------------------------------
  3.8.1 已经打通的部分(可复用)
   1) 自己写了一个**极简 RTSP 客户端** tools/rtsp2lcd.c, 实测与板上
      sample_vi_fd 的 RTSP 服务端(live555 派生, libcvi_rtsp.so)对接成功:
        DESCRIBE -> 200 OK, SDP 拿到 a=control:*
        SETUP    -> 200 OK, Session 拿到
        PLAY     -> 服务端**不返回头部**, 直接在同一 TCP 连接上推 '$' 交织帧
      实测收到的第一包: 24 01 00 30 ... (0x24='$', chn=1, len=0x30)
      ★ 坑: PLAY 之后响应头和 RTP 数据会混在一起收到, 不能盲目读到 \r\n\r\n;
        必须在遇到 '$' 时立刻停手, 并把那段数据搬进帧缓冲, 否则第一包 RTP 会丢。
      ★ 坑: 读响应的循环里不能用 strstr 找 \r\n\r\n, 因为后面混着二进制数据,
        strstr 会被中间的 0 字节截断; 要用 memchr 按长度找。
   2) 交叉编译用的 ffmpeg 头文件: 板上的 libavcodec/avformat/avutil 是

3.12 ★ 精确卡点记录: rtsp_next_nal 的包重组逻辑有 bug(未修好)
--------------------------------------------------------------------------------
  实测状态(诊断日志 /tmp/rtsp2lcd.log, 已加独立日志便于卡死时也能看):
      启动: url=rtsp://127.0.1.1/h264
      TCP 已连接 127.0.1.1:554
      RTSP 建链成功, g_blen=228 SPS=0 PPS=0
      !! iter=2000000 bpos=0 blen=632 byte@bpos=24 NAL=0
         | 前16字节: 24 00 05 B0 80 60 78 28 6D B7 06 6B 28 4C 6A 2B
      (之后 iter=4M/6M/8M... 状态**完全不变** -> 死循环, 一个 NAL 都没解析出来)

  1) 已确认的事实:
       a) RTSP 协议本身是通的: DESCRIBE/SETUP/PLAY 全部成功。
       b) 确实收到了交织 RTP 数据: 24='$', chn=0x00, plen=0x05B0=1456;
         RTP 头 80 60 78 28 -> V=2, 无填充/扩展, CC=0, M=0, PT=96(动态)。
       c) ★ 关键: `bpos=0 blen=632` 但**交织头声明的长度是 1456**
         (0x05B0)。即缓冲区里只有 632 字节, 而这一包需要 4+1456=1460 字节。
         `g_bpos + 4 + plen > g_blen` -> 632 < 1460 -> 走"包跨缓冲区"分支。
       d) 该分支本应: memmove 残留到开头 -> recv 补齐 -> continue。
         但日志显示状态**一个字节都没变**(bpos 仍 0, blen 仍 632),
         说明要么没走到 recv, 要么 recv 立刻返回 0 且没被记录。
  2) 怀疑点(留给下一轮, 按可能性排序):
       a) `iter` 计数与实际状态不同步: 日志每 200 万次才打一次, 且 dbg 只在
          首次打开文件时 "w" 截断、之后追加 —— **看日志时要确认看到的是最新
          那几行, 别被旧行误导**(这一轮就被误导过好几次)。
       b) 跨包分支里的 memmove 参数: `left = g_blen - g_bpos` 在 bpos=0 时
          等于 blen, 分支内再判 `g_bpos > 0` 才 memmove, 于是什么都没做,
          但 `g_blen = left` 也没变 -> 状态确实应该不变。所以问题可能是
          **这个分支被反复进入却没有去 recv**。建议直接重写这段:
          把"读满一包"做成一个独立函数(循环 recv 直到攒够 4+plen 字节),
          逻辑会清晰很多, 不要再在一个大 for(;;) 里混着做。
       c) SO_RCVTIMEO 已设 5 秒, 但从未看到 "recv 返回 ..." 的日志,
          说明**根本没执行到 recv**。优先验证这一点。
  3) 建议的下一步: 先写一个**最小复现**: 只做 DESCRIBE/SETUP/PLAY, 然后把
     收到的原始字节**全部 dump 到文件**(不解析), 用 PC 端脚本离线分析
     RTP 分帧, 确认分帧逻辑对了再回到板上跑。这样比在板上反复试快得多。
     (板子上编译-传输-重启一轮要 3~4 分钟, PC 上分析是秒级的。)

5.1 VPSS group 会残留, 只能重启清
--------------------------------------------------------------------------------
  1) 现象(实测复现): 程序被 kill -9 或段错误退出后, 再跑任何用 VI/VPSS 的程序
     都报:
       [SAMPLE_COMM_VPSS_Init]-28: CVI_VPSS_CreateGrp(grp:0) failed with 0xc0068004!
     0xc0068004 解码(见 cvi_errno.h 的 CVI_DEF_ERR):
       [23:16]=0x06 模块=VPSS, [15:13]=4 等级=ERROR, [12:0]=4 => EN_ERR_EXIST
     即"资源已存在" —— VPSS group 0 还占着。
  2) 内核日志佐证:
       vpss_open: open 2 times
       vpss_create_grp:3331(): Grp(0) is occupied
  3) 为什么: 板上那套 VPSS 模块**不在进程退出/fd 关闭时清理 group**,
     而 group 是内核态资源。所以进程死了, group 还在。
     (这正是用户最初"摄像头测试失败"时那个 VPSS 报错的成因。)
  4) 清理办法(按顺序):
       a) 先 killall -9 掉残留进程; 注意**僵尸进程(Z 状态)是杀不掉的**, 那没关系,
          它已经不放 fd 了;
       b) 确认没人开着 /dev/cvi-vpss:
            for p in /proc/[0-9]*; do for fd in $p/fd/*; do \
              [ "$(readlink $fd)" = /dev/cvi-vpss ] && echo "pid=${p#/proc/}"; done; done
       c) 如果 group 仍被占, **只能 reboot**;
       d) 模块本身卸不掉: lsmod 里 cv181x_vpss 的引用计数由 cv181x_mipi_tx 持有,
          rmmod cv181x_vpss 一定报 Resource temporarily unavailable, 别浪费时间。
  5) 预防: 给工具加信号处理, 退出前显式 DestroyGrp; 调试时不要用 kill -9。

5.2 跑之前先确认没有别的程序占着 VI/VPSS
--------------------------------------------------------------------------------
  1) camera-test.sh / sample_vi_fd 都会占 VI+VPSS; 它们没退干净时, 本工具必然
     CreateGrp 失败。
  2) 固定检查:
       ps | grep -E '[s]ample_vi_fd|[c]am_lcd'
