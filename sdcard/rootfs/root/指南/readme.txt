================================================================================
  指南目录 /root/指南/ —— 这些文件该怎么写
================================================================================

【这个目录是干什么的】
保存"这块开发板相关的一切操作指南与变更记录"。目的只有一个:
让任何一个后来接手的人 —— 可能是几周后的自己, 也可能是别人 —— 手里只有这块板子
和这个目录, 就能把编译环境搭起来、把固件编出来、把功能跑起来、把坑绕过去。

【命名规则】
  1. 记录文件按"当天日期"命名, 形如:  YYYY.M.D.txt
     例: 2026.9.28.txt   (2026 年 9 月 28 日; 月/日不补 0)
  2. 一天一个文件。同一天里后续所有事情都往同一个文件里追加, 不要再建第二个。
  3. readme.txt 固定是"本说明", 任何情况下都不要往里写当天的工作记录。
  4. 有新约定、新坑、新结论, 写进"当天那个文件"; 不要回头改历史文件,
     除非是订正明确的错误(订正要留痕)。

【一天的文件里写什么】
固定分两部分:

  一、环境与约定
      —— "下一个接手的人必须先知道, 否则寸步难行"的东西, 都放这里。例如:
         · 编译环境在哪: 哪台机器 / 什么发行版 / SDK 路径 / 工具链路径
         · 命令怎么发: 从 Windows 怎么进 WSL、脚本要写成什么形式才不会被吃掉
         · 板子怎么连: IP、用户名、密码、USB 网卡
         · 有哪些"不照做就必然踩坑"的硬规矩
      —— 这部分是累积性的: 新一天发现新约定, 就写进当天文件, 不用重写旧的。

  二、当日操作记录
      —— 按时间顺序, 一条一件事, 从早到晚。

【每一条记录的格式】
      YYYY-MM-DD HH:MM | 改动人 | 做了什么 / 为什么 | 完整可复制的命令 | 结果

  硬性要求:
  1. 时间精确到分钟, 24 小时制本机时间(UTC+8), 写在每条最前面。
     当天确实取不到准确时间的(旧记录、别人的记录), 只写日期即可 —— 不要编时间。
  2. 命令必须写成"可以直接复制粘贴执行"的完整形式。不要凭记忆简写、
     不要用 "..." 省略、不要把多条命令挤在一行。只写你真正跑过并验证成功的。
  3. 涉及固件、镜像、内存地址的改动, 一定写清: 目标地址 + 校验方式(md5 / 读回比对)。
  4. 只写事实与结论 —— 现象、根因、改法、验证数据。不写"应该""大概""估计"。
  5. 踩了坑要连"错误示范"一起写, 并标明"不要照抄", 后面的人才知道边界在哪。

【安全铁律(每一次都要守住)】
  ★ fip.bin 是唯一的引导固件, 不要随手动它。本板有 SD 读卡器, 最坏情况可以重写整卡
    救回来, 但要拆机取卡、代价高。除非"常驻跳板本身要改"或"热更后小核彻底起不来",
    否则改小核固件一律走"热更" —— 它不碰 fip.bin、不重启系统。
  ★ 万一必须重打包 fip, 做完必须做字节级校验: 除小核固件段(BLCP_2ND)外,
    其余内容逐字节不变。
  ★ 密钥、token、密码一律不要写进本目录。凭证一旦泄露, 立刻去平台吊销。

【和 PC 上仓库的关系】
  板子上的改动, 记得同步回 PC 仓库 duo256m-lcd-rtos, 再 push 到 GitHub
  (https://github.com/ewfgwae/milkvduo256m)。否则下次换了卡、丢了板子,
  就只剩这一份 SD 卡可依赖。
  仓库里对应的位置: sdcard/rootfs/root/指南/
