★ 安全铁律 (三条, 每次动手前先过一遍)
  1) fip.bin 是唯一的引导固件, 不要随手动它。本板有 SD 读卡器, 最坏情况可以重写整卡
     救回来, 但要拆机取卡、代价高。
  2) 改小核固件一律走"热更"(见第五章) —— 它不碰 fip.bin、不重启系统。
     只有"常驻跳板本身要改"或"热更后小核彻底起不来"才动 fip(见 5.3)。
  3) 万一必须重打包 fip, 做完必须做字节级校验: 除小核固件段(BLCP_2ND)外, 其余逐字节不变。

1.2 从 Windows 调 WSL 的规矩  (每一条都是踩过坑总结出来的)
--------------------------------------------------------------------------------
  1) ★ 多行/复杂命令必须先写成 .sh 文件再执行, 不要用内联引号:
       禁止: wsl -d Ubuntu-22.04 bash -lc "..."
       —— PowerShell 会把 $、&&、管道、引号全吃掉(历史上就是这么把工具链 PATH 搞丢的)。
     正确两步:
       (1) 把脚本写到  C:\Users\1\AppData\Local\Temp\xxx.sh
       (2) 执行        wsl -d Ubuntu-22.04 bash /mnt/c/Users/1/AppData/Local/Temp/xxx.sh
  2) ★ 编小核固件要用 root 身份进 WSL:
       wsl -d Ubuntu-22.04 -u root bash /mnt/c/Users/1/AppData/Local/Temp/xxx.sh
     原因: build 树里有上百个 root 属主的文件, 用 chen 跑会卡在
           "Error writing to build log: Permission denied"; 而 sudo 要输密码。
  3) ★ 编译前必须先手工 export 工具链 PATH:
       export PATH=/home/chen/duo-sdk-v2/host-tools/gcc/riscv64-elf-x86_64/bin:$PATH
  4) 读 WSL 里的文件用 UNC 路径:  \\wsl.localhost\Ubuntu-22.04\home\chen\...
  5) Windows 的 D 盘在 WSL 里是 /mnt/d/...   (路径带空格要加引号)

--------------------------------------------------------------------------------

       nm ~/duo-sdk-v2/freertos/cvitek/install/bin/cvirtos.elf \
          | grep -E 'g_lvgl_probe|g_dma_probe|g_spi2_probe'
  2) 读法: 第 n 项的地址 = g_lvgl_probe + n*8; 一律用 width=32 逐项读最省心
     (本机 busybox 的 devmem 对 64 位读法结果不稳定, 32 位逐项读最可靠)。
     下面这组地址对应 build id 0x484A0004 的固件:
       devmem 0x8fe6cb20 32     # [0]  'LVGL' 魔数头 (0x4C56474C)
       devmem 0x8fe6cb28 32     # [1]  0x600D = demo+OSD 已建完
       devmem 0x8fe6cb30 32     # [2]  主循环圈数(隔几秒读两次, 在涨 = 小核在跑)
       devmem 0x8fe6cb58 32     # [7]  帧率 x10 (例: 0x1BF = 447 -> 44.7 FPS)
       devmem 0x8fe6cb68 32     # [9]  送显耗时 us/秒   ┐
       devmem 0x8fe6cb70 32     # [10] LVGL 处理耗时 us/秒 ├ 定位瓶颈用(见 lvgl_task.c)
       devmem 0x8fe6cb78 32     # [11] 推给屏的像素数/秒 ┘
       devmem 0x8fe6cb90 32     # [14] 固件 build id (0x484A0004 = 'HJ' + 序号)
       devmem 0x8fe6cb98 32     # [15] 'MONR' 魔数尾 (0x4D4F4E52)
  3) 常驻热更跳板首条指令(应为 0x30401073):
       devmem 0x8ff90000 32
  4) sysDMA 自检探针 g_dma_probe[16] (见 6.2):
       devmem 0x8fec4c78 32     # [13] 自检结果码, 0 = 成功
  5) SPI2 送显 DMA 探针 g_spi2_probe[8] (见 6.4):
       devmem 0x8fec8168 32     # [5]  DMA 失败回退 PIO 次数, 0 = DMA 全通

================================================================================
 五、烧录 / 更新小核固件 —— 现在走"热更", 不用烧 fip、不用重启
================================================================================
【结论】
  1) 小核固件现在是"热更": 大核程序把新固件直接写进小核内存区, 小核自己跳过去重新跑。
  2) 全程不动 fip.bin, 不重启系统, 不存在变砖路径。
  3) 只有极特殊情况(见 5.3)才需要重烧 fip。

5.1 小核固件热更(日常唯一做法)
--------------------------------------------------------------------------------
  1) 板上一条命令:
       /root/lcd_sender rtos /root/cvirtos.bin
  2) 完整流程(本机 -> 板子):
       # 1) 本机重新编译小核固件
       cd ~/duo-sdk-v2 && source build/envsetup_milkv.sh milkv-duo256m-glibc-arm64-sd
       cd build && make rtos
       # 2) 推上去
       scp ~/duo-sdk-v2/freertos/cvitek/install/bin/cvirtos.bin root@192.168.42.1:/root/cvirtos.bin
       # 3) 板上热更
       ssh root@192.168.42.1 '/root/lcd_sender rtos /root/cvirtos.bin'
  3) 正常输出:
       固件 /root/cvirtos.bin: 1640640 字节 = 应用区 1638400 + 常驻跳板 2240 (跳板不重写)
       小核已停在跳板 (0.0 ms), 开始往 0x8FE00000 写 1638400 字节
       /dev/mem 写入 + 读回校验通过
       已置 ctrl.reload=0x484F544A, 等新固件启动...
       热更完成: 新固件已运行 (state=1, ~200 ms)        <- 退出码 0 = 成功
  4) 验证(隔几秒各读两次, 地址随固件变, 见 4.5):
       devmem 0x8fe6cb30 32     # [2] 主循环圈数在涨 = 新固件在跑
       devmem 0x8fe6cb90 32     # [14] 应等于本次固件的 build id

5.2 内存布局(热更为什么安全)
--------------------------------------------------------------------------------
  1) 0x8FE00000 .. 0x8FF90000   小核应用区  (1638400 字节, 热更时原地覆盖)
  2) 0x8FF90000 .. 0x8FFC0000   常驻热更跳板 .hotjump (约 2 KB, 永不覆盖)
  3) 0x8FFC0000 ..              LCD 共享内存
  4) 大核只写"应用区", 物理上碰不到跳板和共享内存; 写完还会逐字节读回校验,
     不符就不放行起跳 —— 最坏只是小核没能重启, 重启板子即回旧固件。
  5) 跳板执行期间还会做一次全 cache 失效, 防止旧固件的脏 cache 行回写覆盖新固件。

5.3 极端情况: 重烧 fip.bin (会重启一次, 慎用!)
--------------------------------------------------------------------------------
  1) 仅在如下情况使用:
       - 常驻跳板本身(hotjump.S)需要修改;
       - 或热更后小核彻底起不来。
  2) 打包: 以板卡当前 fip 作底, 只替换 BLCP_2ND(小核固件)段
       python3 ~/duo-sdk-v2/fsbl/plat/cv181x/fiptool.py genfip \
           --OLD_FIP <板卡当前 fip.bin> \
           --BLCP_2ND ~/duo-sdk-v2/freertos/cvitek/install/bin/cvirtos.bin \
           <输出的新 fip.bin>
  3) ★ 打包后必须先做字节级校验, 确认除 BLCP_2ND 段外其余内容逐字节不变!
  4) 历史: 板卡当前 fip.bin 的 md5 应为 a5a5ca0109d98e238ac82c0aae6d175a
  5) 备份: 板子上历史 fip 备份在 /boot/fip.bin.bak_*

 六、常见故障与排查
================================================================================

6.1 【必看】热更/通讯报 "No buffer space available"、ping 发不出去
--------------------------------------------------------------------------------
  1) 现象:
       a) /root/lcd_sender rtos /root/cvirtos.bin
            -> ioctl RTOS_CMDQU_SEND: No buffer space available
       b) 或 /root/lcd_sender ping 直接失败;
       c) dmesg 里能看到 "No valid mailbox is available"。
  2) 原因:
       a) 大小核之间的 IPCM mailbox 一共只有 8 个槽位(物理地址 0x1900400 起, 每槽 8 字节)。
       b) 若大核进程(比如后台的 `lcd_sender mon`)被 kill -9 强杀, 它已经发出、小核
          也已回复的那条消息就没人接手, 槽位的 linux_valid/rtos_valid 两位会一直停在
          1、永不释放。
       c) 8 个槽位被这种"孤儿回执"占满后, 之后任何发送都会返回 ENOBUFS。
       d) 这不是固件坏了, 只是邮箱满了。
  3) 修复: 清零 8 个槽位(只腾空邮箱, 不影响正在跑的小核固件):
       i=0; while [ $i -lt 8 ]; do a=$((0x1900400 + i*8)); devmem $(printf 0x%x $a) 64 0; i=$((i+1)); done
     然后 /root/lcd_sender ping 应立即恢复正常。
  4) 预防:
       a) 停 lcd_sender 优先用 `killall lcd_sender`(发 SIGTERM 让它自己收尾);
       b) 只有卡死才用 `killall -9 lcd_sender`, 且用完务必先清槽位再热更。
  5) 查看槽位占用(每槽 8 字节, 非 0 即占用; 正常空闲时全 0):
       devmem 0x1900400 64 ; devmem 0x1900408 64 ; ... ; devmem 0x1900438 64

6.2 小核 sysDMA 自检探针
--------------------------------------------------------------------------------
  1) 小核固件启动时会调 sysdma_selftest() 做一次 4096 字节的内存到内存搬运, 用来确认
     C906L 能否驱动 SoC 的 sysDMA(DesignWare AXI DMAC, 基址 0x04330000)。
  2) 结果放在 g_dma_probe[16](地址用 `nm cvirtos.elf | grep g_dma_probe` 查):
       devmem 0x8fec4c78 32     # [13] 结果码: 0=成功; 0xE1=控制器不可见; 0xE2=超时;
                                #      0xE3=数据不对; 0xE5=通道被占
       devmem 0x8fec4c68 32     # [11] 不一致字节数, 应为 0
  3) 说明: 借的是 sysDMA 的空闲通道 6(大核 dw_dmac 正在用 0..3), 且不碰全局 RESET/CFG,
           与 Linux 侧共存。
  4) 说明: 小核读 DMAC_ID 恒为 0(本 SoC 如此), 存在性要看 DMAC_COMPVER。

6.3 【编译坑】改了源码, 热更后行为却没变
--------------------------------------------------------------------------------
  1) 现象: 明明改了 .c 文件, 编译也过了, 热更后固件行为还是旧的(探针数值不变)。
  2) 原因: `make rtos` 对已存在的 .obj 有时不重编(陈旧对象被直接复用)。
           注意: 顶层 `~/duo-sdk-v2/build` 只是转调, 真正的对象树在
           ~/duo-sdk-v2/freertos/cvitek/build/。
  3) 处理: 删掉对应 .obj 和 libcomm.a 再编, 例如:
       cd ~/duo-sdk-v2/freertos/cvitek/build
       rm -f task/comm/CMakeFiles/comm.dir/src/riscv64/<文件名>.c.obj task/comm/libcomm.a
       cd ~/duo-sdk-v2/build && make rtos
  4) ★ 更省事的做法(只重编改动的那一层, 实测可靠):
     对象路径规律是 <子目录>/CMakeFiles/<目标>.dir/<源文件>.c.obj, 例如改 lvgl_task.c:
       cd ~/duo-sdk-v2/freertos/cvitek/build/task
       rm -f lvgl/CMakeFiles/lvgl.dir/lvgl_task.c.obj
       cmake --build . --target install && cmake --build . --target cvirtos.bin
       # 产物: ~/duo-sdk-v2/freertos/cvitek/install/bin/cvirtos.bin
  5) 验证: 用反汇编确认新代码确实进了 ELF(把 <函数名>/<特征立即数> 换成你自己的):
       ~/duo-sdk-v2/host-tools/gcc/riscv64-elf-x86_64/bin/riscv64-unknown-elf-objdump \
           -d --disassemble=<函数名> ~/duo-sdk-v2/freertos/cvitek/install/bin/cvirtos.elf \
           | grep -i <特征立即数>

6.4 小核 SPI2 送显-DMA 探针
--------------------------------------------------------------------------------
  1) 小核刷屏的 spi2_write_dma() 每搬一块数据就把统计写进 g_spi2_probe[8]
     (地址用 `nm cvirtos.elf | grep g_spi2_probe` 查; build id 0x484A0004 对应 0x8fec8140)。
  2) 第 n 项的地址 = 基址 + n*8:
       devmem 0x8fec8140 32     # [0] 魔数 'SDM2' (0x53444D32), 不匹配说明地址过期
       devmem 0x8fec8148 32     # [1] DMA 调用次数 (隔几秒读两次, 在涨 = 确实在走 DMA)
       devmem 0x8fec8150 32     # [2] DMA 累计字节数
       devmem 0x8fec8158 32     # [3] 最近一次返回码 0 = 成功 (非 0 见 6.5)
       devmem 0x8fec8160 32     # [4] SPI FIFO 深度(实测 16)
       devmem 0x8fec8168 32     # [5] ★ DMA 失败回退 PIO 的次数, 0 = SPI2 送显已全程走 DMA
       devmem 0x8fec8170 32     # [6] 写进 DMATDLR 的水位(8)
       devmem 0x8fec8178 32     # [7] 目的端 MSIZE 编码(2 = 一次 8 项)
  3) 判据: [5]==0 且 [3]==0 即 DMA 通路完全生效, 一次都没退回逐字节轮询。
  4) 参考寄存器(基址 0x04330000 的 sysDMA, 小核借的是通道 7):
       devmem 0x04330820 64     # ch7 CFG: 正常应含 SRC_PER=DST_PER=5 (5 = SPI2_TX 请求线)
       devmem 0x04330018 64     # ch7 CH_EN: 刷新期间读到 bit7=1(0x80) 是正常的(正在搬);
                                #           长时间空闲时若仍为 1, 说明通道卡住, 需查 6.5

6.5 【重要】SPI2 送显 DMA 不生效(DMA 一次都没搬成)
--------------------------------------------------------------------------------
  1) 现象:
       a) g_spi2_probe[1](DMA 次数) 不涨;
       b) [5](回退 PIO 次数) 一直涨;
       c) [3] 非 0;
       d) ch7 CH_EN(0x04330018) 的 bit7 恒为 1、BLOCK_TS 不动 —— 通道"已使能、等握手"卡死。
  2) 根因(已修): SPI2 的 DMA 请求线映射必须对。板级 DTS 写的是
       dmas = <&dmac 4 1 1>   /* rx: SPI2_RX */
              <&dmac 5 1 1>;  /* tx: SPI2_TX */
     即 4 = SPI2_RX、5 = SPI2_TX。送显只发不收, 请求线必须用 5;
     若误填 4, TX-only 时 RX FIFO 永不进数据, 请求线永不置起, 通道就永远卡在等握手。
  3) 自查: 板子上 `cat /proc/device-tree/sysdma_remap/ch-remap` 应看到
           槽位 4=0x14(=20=CVI_SPI2_RX)、槽位 5=0x15(=21=CVI_SPI2_TX)。
  4) 另外: 启动 DMA 前要先"中止"可能残留的脏通道(CH_EN 的 ABORT 位在 bit32,
           写使能在 bit40), 只有中止不掉才判"通道被占"(返回 0xE5)。
