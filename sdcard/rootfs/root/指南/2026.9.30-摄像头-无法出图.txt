★ 安全铁律 (三条, 每次动手前先过一遍)
  1) fip.bin 是唯一的引导固件, 不要随手动它。本板有 SD 读卡器, 最坏情况可以重写整卡
     救回来, 但要拆机取卡、代价高。
  2) 改小核固件一律走"热更"(见 2026.9.28-小核-帧率修复与热更.txt 第五章) —— 它不碰 fip.bin、不重启系统。
  3) 万一必须重打包 fip, 做完必须做字节级校验: 除小核固件段(BLCP_2ND)外, 其余逐字节不变。

================================================================================
  一、环境与约定  (接手的人必须先知道的一切)
================================================================================

1.1 摄像头硬件
--------------------------------------------------------------------------------
  1) 模组: Milk-V CAM-GC2083 (格科微 GC2083, 200 万像素, MIPI CSI)。
  2) 接口: 板上 16P MIPI CSI 座(FPC 排线)。
  3) 供电: 由板子提供 3V3; 电平 1.8V 域, 切勿接 5V。
  4) 排线朝向: 金手指方向插错是最常见的"完全没反应"原因, 插法与屏一样要看清楚再上电。

1.2 摄像头在 Duo256M 上的引脚占用 (决定性事实, 与 LCD 不冲突)
--------------------------------------------------------------------------------
  1) 摄像头 I2C 走的是 **I2C2**, 引脚是 MIPI 那几个 pad, 不是 40PIN 排针:
       PAD_MIPI_TXM1 = IIC2_SDA   (板上丝印 GP10)
       PAD_MIPI_TXP1 = IIC2_SCL   (板上丝印 GP11)
       PAD_MIPI_TXP0 = CAM_MCLK0  (传感器主时钟)
       PAD_MIPI_TXP2 = XGPIOC_17  (传感器 RESET, 低有效, 板上丝印 GP12)
     出处: build/boards/cv181x/sg2002_milkv_duo256m_glibc_arm64_sd/u-boot/cvi_board_init.c
  2) LCD 走的 SPI2 用的是 SD1_* 那组 pad (GP6~GP9), I2C1 用 SD1_D2/D1 (GP4/GP5)。
  3) 结论: 摄像头(I2C2/GP10~GP12 + MIPI 差分对) 与 LCD(SPI2/GP6~GP9 + DC/RES/BLK)
     用的pad **完全不重叠**。所以"装了 LCD" 不可能把摄像头挤掉, 排障时不要往这边想。
  4) 寄存器对照表(FMUX, 基址 0x03001000), 板上实测值在括号里:
       devmem 0x030011AC 32   # PAD_MIPI_TXM1 -> IIC2_SDA, 正常 = 0x4
       devmem 0x030011B0 32   # PAD_MIPI_TXP1 -> IIC2_SCL, 正常 = 0x4
       devmem 0x030011B8 32   # PAD_MIPI_TXP0 -> CAM_MCLK0, 正常 = 0x4
       devmem 0x030011A8 32   # PAD_MIPI_TXP2 -> XGPIOC_17, 正常 = 0x3

1.3 I2C 总线号与控制器物理地址的对应 (务必记住)
--------------------------------------------------------------------------------
  1) I2C1_BASE = 0x4010000 -> i2c-1  -> 引脚 GP4/GP5
  2) I2C2_BASE = 0x4020000 -> i2c-2  -> 摄像头, 引脚 GP10/GP11
  3) I2C3_BASE = 0x4030000 -> i2c-3
  4) 出处: freertos/cvitek/hal/cv181x/config/top_reg.h 第 32~36 行。
  5) 用途: 内核打印里的 "i2c_designware 4010000.i2c: controller timed out" 指的是
     **i2c-1**, 不是摄像头那条总线。看到这条不要误判成摄像头有问题。

1.4 传感器配置文件
--------------------------------------------------------------------------------
  1) 路径: /mnt/data/sensor_cfg.ini, 是个软链接, 指向 sensor_cfg_GC2083.ini。
  2) 本板当前内容(与官方 SDK 模板逐字节一致):
       [source]  dev_num = 1
       [sensor]  name = GCORE_GC2083_MIPI_2M_30FPS_10BIT
                 bus_id = 2
                 sns_i2c_addr = 37      (即 7bit 地址 0x37)
                 mipi_dev = 0
                 lane_id = 1, 0, 2, -1, -1
                 pn_swap = 0, 0, 0, 0, 0
  3) 官方模板位置: $SDK/device/generic/rootfs_overlay/duo256m/mnt/data/sensor_cfg_GC2083.ini
  4) GC2083 的 I2C 地址是 0x37, 所以"扫总线时找 0x37"就是找摄像头。

1.5 测试程序在哪 (踩过的坑, 极易误判)
--------------------------------------------------------------------------------
  1) 测试脚本: /mnt/system/usr/bin/camera-test.sh, 内容只有两行有效:
       export LD_LIBRARY_PATH=/mnt/system/lib:/mnt/system/usr/lib:/mnt/system/usr/lib/3rd
       sample_vi_fd /mnt/cvimodel/scrfd_768_432_int8_1x.cvimodel
  2) 它调的是 PATH 里的 sample_vi_fd, 而 PATH 由 /etc/profile 追加
     /mnt/system/usr/bin —— 也就是说 **只有登录 shell 才找得到**。
  3) /root 下那个 sample_vi_fd 只有 23048 字节, 与 /mnt/system/usr/bin/ai/sample_vi_fd
     (155960 字节) **不是同一个东西**。/root 那个实测连中间件都不进, 只报
     "Failed to get senor infomation from ini file"; 真正能测摄像头的只有
     /mnt/system/usr/bin/ai/sample_vi_fd。
  4) 所以在 /root 下直接敲 camera-test.sh, 实际跑的是 /root/sample_vi_fd —— 靠"当前
     目录也在 PATH 里"才跑起来的, 换目录就报 not found。要复现必须写绝对路径:
       /mnt/system/usr/bin/ai/sample_vi_fd /mnt/cvimodel/scrfd_768_432_int8_1x.cvimodel

1.6 摄像头相关的内核模块 (原厂 loadsystemko.sh 已在加载)
--------------------------------------------------------------------------------
  1) /mnt/system/ko/ 下与摄像头有关的是:
       cvi_mipi_rx.ko    MIPI CSI 接收(含 snsr-reset 引脚控制)
       snsr_i2c.ko       传感器 I2C
       cv181x_vi.ko      VI
       cv181x_base.ko / cv181x_sys.ko / cv181x_vpss.ko / cv181x_dwa.ko
  2) 传感器驱动本体在用户态库里, 不在 ko 里:
       /mnt/system/usr/lib/libsns_full.so
       源码路径(编译时): cvi_mpi/component/isp/sensor/cv181x/gcore_gc2083/gc2083_cmos.c
   3) 打印 "family ID request : receive error" 的字符串在 /mnt/system/usr/lib/libsys.so,
      含义 = 驱动读传感器 ID 失败, 也就是 I2C 上没有应答。
  4) /dev/cvi-vo 不存在 —— 因为 loadsystemko.sh 里 cv181x_vo.ko 是注释掉的。
     这一条只是提示("Cannot open '/dev/cvi-vo': 2"), 与本测试能否出图 **无关**,
     不要把它当成失败原因。

================================================================================
  二、2026-09-30 的排障结论 (先说结论, 判据在下一章)
================================================================================

  1) 现象: 板上跑 camera-test.sh, 最后停在
       [SAMPLE_COMM_VI_StartMIPI]-494: sensor 0 stDevAttr.devno 0
       vi init failed. s32Ret: 0xffffffff !
       init middleware failed! ret=ffffffff
     并且前面有一行 family ID request : receive error。
  2) 结论: **SoC 侧的软件与引脚配置全部正确; 失败点在"摄像头本体没有应答"**,
     属于硬件/接线/供电层面的问题 —— 具体就是: 那条 I2C2 总线上一个器件都没有,
     i2cdetect 全 " -- "。
  3) 也就是说: 这不是固件不对、也不是"LCD 抢了引脚"、更不是 camera-test.sh 坏了,
     而是 **模组、排线、座子这三者之间没通**。
  4) 因此正确的第一步不是改配置, 而是: 断电 -> 重新插好 FPC 排线(金手指朝向要对) ->
     上电 -> 跑 1.5 节第 4) 条那条绝对路径命令。

================================================================================
  三、判据: 每一步做了什么、看到什么 (可复现)
================================================================================

3.1 判据一: 传感器配置正确
--------------------------------------------------------------------------------
  1) 命令:
       ls -l /mnt/data/sensor_cfg.ini
       cat /mnt/data/sensor_cfg.ini
  2) 结果: 软链接 -> sensor_cfg_GC2083.ini; 内容与 1.4 节第 2) 条完全一致;
     与官方模板 device/generic/rootfs_overlay/duo256m/mnt/data/sensor_cfg_GC2083.ini
     逐字节相同。 => 配置层排除。

3.2 判据二: 摄像头 I2C 引脚复用正确
--------------------------------------------------------------------------------
  1) 命令:
       devmem 0x030011AC 32
       devmem 0x030011B0 32
       devmem 0x030011B8 32
       devmem 0x030011A8 32
  2) 结果: 0x00000004 / 0x00000004 / 0x00000004 / 0x00000003。
  3) 对照 1.2 节第 4) 条的期望值 —— 四项全中。 => SoC 引脚没切错, 排除。
  4) 同时读 LCD 那边(SD1 组)确认没有被改坏:
       devmem 0x030010E4 32   # SD1_CLK -> SPI2_SCK, = 0x1
       devmem 0x030010E0 32   # SD1_CMD -> SPI2_SDO, = 0x1
       devmem 0x030010D0 32   # SD1_D3  -> SPI2_CS_X,= 0x1
     实测都是 0x1, 屏照常工作。

3.3 判据三: 摄像头总线上一片空白 (决定性证据)
--------------------------------------------------------------------------------
  1) 命令:
       i2cdetect -l
       i2cdetect -y -r 1
       i2cdetect -y -r 2
       i2cdetect -y -r 3
  2) 结果: i2c-1 / i2c-2 / i2c-3 三条总线都是满屏 " -- ", 没有任何地址应答;
     期望出现 0x37(GC2083) 的位置也是 " -- "。
     连"边跑测试边扫"都扫不到(测试程序正在反复读传感器时同样没有 0x37)。
  3) 注意: 扫的时候没有报 "controller timed out", 说明控制器本身是好的、
     时钟在走, 只是没有任何器件拉低 SDA 应答。 => 问题在总线之外(模组/排线/座子)。

3.4 判据四: 完整复现失败, 且确认只有真测试程序能测
--------------------------------------------------------------------------------
  1) 命令:
       export LD_LIBRARY_PATH=/mnt/system/lib:/mnt/system/usr/lib:/mnt/system/usr/lib/3rd
       cd /root
       timeout 30 sh -lc 'camera-test.sh'
  2) 结果(与最初现象逐行一致):
       Cannot open '/dev/cvi-vo': 2, No such file or directory
       family ID request : receive error
       [SAMPLE_COMM_SNS_ParseIni]-2219: Parse /mnt/data/sensor_cfg.ini
       ... (解析结果与 1.4 节一致) ...
       MMF Version:6b03c2762-64bit
       Create VBPool[0..2] / Total memory of VB pool: 30758400 bytes
       Initialize SYS and VB
       Initialize VI
       ISP Vipipe(0) Allocate pa(...) va(...) size(311592)
       stSnsrMode.u16Width 1920 stSnsrMode.u16Height 1080 30.000000 wdrMode 0
       [SAMPLE_COMM_VI_StartMIPI]-494: sensor 0 stDevAttr.devno 0
       vi init failed. s32Ret: 0xffffffff !
       init middleware failed! ret=ffffffff
  3) 对照实验: 同一目录下跑 /root/sample_vi_fd 只输出到
       Failed to get senor infomation from ini file (/mnt/data/sensor_cfg.ini).
     就到头了(退出码 255), 根本进不到 MMF。证明 1.5 节第 3) 条的判断 ——
     /root 那个不是真测试程序。

3.5 判据五: 复位脚没有被软件拉高 (次要疑点, 记下来备用)
--------------------------------------------------------------------------------
  1) 命令(注意 GPIOC 的寄存器偏移, 不是 0x...000/0x...004):
       devmem 0x03022018 32   # SWPORTC_DR  实测 0x00000000
       devmem 0x0302201C 32   # SWPORTC_DDR 实测 0x00000000
  2) 含义: GPIOC 整口既没配成输出、也没输出高电平; bit17 就是传感器 RESET。
     按 mipi_rx 设备树 snsr-reset = <&portc 17 GPIO_ACTIVE_LOW> 的语义, 正常工作时
     应为输出高(复位释放)。
  3) 说明: 手动经 devmem 把 bit17 写 1、再补一次"低->高"脉冲, 总线依然全 "--"。
     所以"复位没释放"最多是次要因素, **不是**本次的主因; 但排线插好之后如果还是
     扫不到, 这里是第二个要查的点(见 5.1 第 6) 条)。
  4) 注意: 本节两条只读命令无副作用; 3) 里写的 devmem 是写入操作, 属于实验性质,
     不要在生产状态下随手跑。真正的复位控制应该由 cvi_mipi_rx.ko 负责。

================================================================================
  四、板上一条命令自检 (camera-diag.sh)
================================================================================

4.1 脚本位置与用法
--------------------------------------------------------------------------------
  1) 板上: /root/camera-diag.sh        仓库: sdcard/rootfs/root/camera-diag.sh
  2) 用法(板上 root):
       chmod +x /root/camera-diag.sh
       /root/camera-diag.sh
  3) 退出码: 0 = 各层自检都过; 非 0 = 至少一层没过(脚本会自己打印结论)。
     板上拿退出码用 `echo $?`, 别靠肉眼判断。

4.2 脚本查什么、怎么下结论
--------------------------------------------------------------------------------
  1) 第 1 步: 打印 sensor_cfg.ini 的关键字段(传感器名/bus_id/地址/lane)。
  2) 第 2 步: 读 1.2 节那 4 个 FMUX 寄存器, 期望 4/4/4/3; 不对就报"SoC 侧引脚没切到 I2C2"。
  3) 第 3 步: 依次扫 i2c-1/2/3, 专门找 0x37。
       a) 找到  -> 打印"接线/供电正常, 问题在软件侧", 可以去跑 camera-test.sh;
       b) 找不到-> 打印"SoC 侧已就绪, 但摄像头没有任何应答: 属于硬件/接线/供电 问题",
                  并列出要查的四项(见 5.1)。
  4) 第 4 步: 把内核日志里 family ID / i2c / sensor / mipi 相关行 tail 出来,
     并注明 "family ID request : receive error" 的含义与第 3 步结论一致。

4.3 为什么值得留这个脚本
--------------------------------------------------------------------------------
  1) 它把"硬件问题"和"软件问题"在一条命令里分开, 省掉反复改配置的瞎试。
  2) 判据是寄存器原始值和扫描结果, 不依赖任何人的主观描述, 换个人跑结论一样。

================================================================================
  五、摄像头起不来时的排查顺序 (按代价从低到高)
================================================================================

5.1 先查硬件 (本次结论指向这里)
--------------------------------------------------------------------------------
  1) 断电 -> 把 FPC 排线拔下重插, 确认插到底、卡扣锁紧。
  2) 确认金手指(金属面)朝向与 milkv.io 文档图示一致 —— 朝向反了会完全没反应。
  3) 确认插的是板上 **16P MIPI CSI** 座, 不是别的排针座。
  4) 万用表量座子第 16 脚对地: 应为 3V3。没电就不是软件问题。
  5) 换一根排线 / 换一个 GC2083 模组交叉验证, 排除排线或模组损坏。
  6) 以上都对且仍扫不到 0x37, 再查 3.5 节的复位脚: 正常应被 cvi_mipi_rx.ko 拉成
     输出高; 若实测长期是 0/高阻, 才需要往这一层深挖。

5.2 再查软件 (只有在 5.1 通过、总线上能看到 0x37 之后才轮到这里)
--------------------------------------------------------------------------------
  1) 用绝对路径跑真测试程序(1.5 节第 4) 条), 不要用 /root 下那个 23048 字节的:
       /mnt/system/usr/bin/ai/sample_vi_fd /mnt/cvimodel/scrfd_768_432_int8_1x.cvimodel
  2) 确认 /dev/i2c-2 存在: ls -l /dev/i2c*
  3) 确认模块都在: lsmod | grep -E 'vi|mipi|snsr|base|vpss'
  4) 确认 sensor_cfg.ini 没被人换成别的模组配置(四个 ini 都在 /mnt/data):
       ls -l /mnt/data/sensor_cfg*.ini
  5) 注意 "Cannot open '/dev/cvi-vo': 2" 是正常的(cv181x_vo.ko 未加载, 见 1.6 节第 4) 条),
     不要为它去改任何东西。

5.3 不要做的事
--------------------------------------------------------------------------------
  1) 不要为了摄像头去动 fip.bin —— 本次现象与 fip 无关。
  2) 不要以为是 LCD 抢了引脚 —— 1.2 节第 3) 条已证明两组 pad 不重叠。
  3) 不要在没确认总线上有 0x37 之前, 反复改 sensor_cfg.ini 的 lane_id / pn_swap。

================================================================================
  六、【根因①】内核模块 snsr_i2c.ko 在开机 insmod 时就崩了 (Kernel Oops)
================================================================================

6.1 现象 (dmesg, 每次开机必现)
--------------------------------------------------------------------------------
  1) 关键几行(实测原文):
       [    5.689691] Unable to handle kernel paging request at virtual address 007265746e692f7e
       [    5.734984] Internal error: Oops: 96000004 [#1] PREEMPT SMP
       [    5.753351] CPU: 0 PID: 172 Comm: insmod Tainted: GF  O  5.10.4-tag- #3
       [    5.772059] pc : is_software_node+0x10/0x34
       [    5.776382] lr : software_node_notify+0x40/0xf4
       [    5.881467] Call trace:
       [    5.877861]  device_add+0x174/0x6a0
       [    5.881467]  platform_device_add+0xec/0x228
       [    5.885790]  platform_device_register+0x54/0x64
       [    5.890475]  init_module+0x28/0x1000 [snsr_i2c]
  2) 那个"虚拟地址" 0x007265746e692f7e 是 ASCII, 解出来是 "~/init..." 这种字符串,
     也就是内核把一个 **字符串指针** 当成了 struct device 的 fwnode 字段去解引用。
  3) 完整日志已存在板上: /root/dmesg_boot.txt (520 行)。
  4) 后果: cvi_snsr_i2c_init() 在第一步 platform_device_register() 就挂了,
     模块自己的三条自打印(Failed to init res for snsr / Failed to register cmm for snsr /
     Can not get cvi_snsr drvdata) **一条都没出现**;
     /sys/bus/platform/devices/ 下也没有 sensor_i2c 平台设备 —— 平台设备确实没建起来。

6.2 这条为什么会让摄像头彻底用不了
--------------------------------------------------------------------------------
  1) 整个 CVITEK 传感器 I2C 通路就是 snsr_i2c.ko 提供的:
       cvi_snsr_i2c_probe() -> vip_sys_register_cmm_cb(0, dev, snsr_i2c_ioctl)
       _init_resource()     -> i2c_get_adapter(i) + i2c_new_client_device(...)
     前者把 snsr_i2c_ioctl 注册给 VIP/SYS 的 CMM 框架(用户态 ISP 库就是调它),
     后者才建出 "sensor_i2c" 这个 I2C 客户端。
  2) 模块 init 崩了 => 这两个都注册不上 => 用户态库读传感器一律失败,
     打印就是我们看到的 "family ID request : receive error"。
  3) ★ 所以先有"模块崩了"这个根因, 才轮到"I2C 上有没有器件"这个问题。
     查摄像头之前必须先确认这个 Oops 不在。

6.3 根因: 板上的 .ko 是**旧的预编译产物**, 与 2026-09-27 重编的内核不匹配
--------------------------------------------------------------------------------
  1) 内核: "Linux version 5.10.4-tag- ... #3 SMP PREEMPT Sun Sep 27 20:42:13 CST 2026",
     构建树 = /home/chen/duo-sdk-v2/linux_5.10
     (build/sg2002_milkv_duo256m_glibc_arm64_sd/vmlinux 的时间戳正是 Sep 27 20:42, 对得上)。
  2) 板上 /mnt/system/ko/*.ko 全部是镜像里带的 **2025-05-30** 预编译产物:
       -rw-r--r-- 1 root root 14632 May 30  2025 /mnt/system/ko/snsr_i2c.ko
       -rw-r--r-- 1 root root 90136 May 30  2025 /mnt/system/ko/cvi_mipi_rx.ko
       -rw-r--r-- 1 root root 463976 May 30  2025 /mnt/system/ko/cv181x_vi.ko
  3) 内核是本工程改过的(见 README 第 7 节: 设备树加 SPI2 的 DMA 请求线 + sysdma_remap
     槽位 4/5、defconfig 相应开关、spidev.c 的 bufsiz 4096->262144)。内核一改一重编,
     和这些旧 .ko 的 ABI 就可能对不上。
  4) 证据(实测): 把 snsr_i2c.ko 反汇编, 看它对 struct platform_device 的字段偏移:
       /home/chen/duo-sdk-v2/host-tools/gcc/gcc-linaro-7.3.1-2018.05-x86_64_aarch64-linux-gnu/bin/aarch64-linux-gnu-objdump \

       1c: 91014295  add x21, x20, #0x50     <- &cvi_snsr_i2c_pdev (.data + 0x50)

     即该 .ko 认为 struct platform_device 占 0x288-0x50 = 0x238 字节、

  5) 一句话: **改了内核重编, 却没有重编 /mnt/system/ko 下的驱动模块。**

6.4 正确修法: 用同一棵内核树重编 ko
--------------------------------------------------------------------------------
  1) 驱动源码(完整可用)整套在:
       /home/chen/milkv-duo256-develop/     <- CVITEK 原厂源码树, 含 osdrv
       /home/chen/milkv-duo256-develop/osdrv/interdrv/snsr_i2c/common/snsr_i2c.c
     注意: 本工程的构建树 /home/chen/duo-sdk-v2 **没有** osdrv 目录, 所以源码要从这棵树拿。
  2) 该模块的官方构建方式(见 osdrv/interdrv/snsr_i2c/Makefile):
       make ARCH=$(ARCH) -C $(KERNEL_DIR) M=$PWD modules
     依赖 base 模块的符号(KBUILD_EXTRA_SYMBOLS = ../base/Module.symvers),
     osdrv 顶层规则也写明 snsr_i2c: base —— 也就是要**先编 base 再编 snsr_i2c**。
  3) ★ 关键: KERNEL_DIR 必须指向"正在跑的那个内核"的构建树, 也就是
       /home/chen/duo-sdk-v2/linux_5.10  (O=build/sg2002_milkv_duo256m_glibc_arm64_sd),
     工具链用 host-tools/gcc/gcc-linaro-7.3.1-2018.05-x86_64_aarch64-linux-gnu/bin。
  4) 编出来的 snsr_i2c.ko 覆盖到板上 /mnt/system/ko/snsr_i2c.ko, 重启(或先
     rmmod/insmod)后确认:
       dmesg | grep -i 'Unable to handle'      # 应无输出
       ls /sys/bus/platform/devices/ | grep sensor   # 应出现 sensor_i2c
       grep 'i2c:-------hook' /root/dmesg_boot.txt   # 应出现 hook 0/1/2/3
  5) 同理: 只要以后**再动内核**, /mnt/system/ko 下的模块都要一起重编, 否则这个 Oops
     会以别的形式再来一次。

     确认驱动模块本身没崩。
  2) 第二步才是: /root/camera-diag.sh —— 确认 I2C 上有没有 0x37。
  3) 两步都过了, 摄像头还不亮, 才轮到怀疑排线/模组。

  七、【根因②·真正的那个】传感器复位脚 XGPIOC_17 从来没被拉高
================================================================================

7.0 ★ 结论先给: 这是"旧预编译 ko + 重编内核"ABI 错位的**第二处**表现
--------------------------------------------------------------------------------
  1) 上游源码(V1/V2 都一样, 已逐行确认)**是对的**, 不需要打补丁。
  2) 真正的修法 = **把 cvi_mipi_rx.ko 也用同一棵内核树重编**, 与根因①同一个道理。
  3) 重编后的驱动实测能自己搞定复位脚(见 7.5), 所以自写的 snsr_rst.ko 只是
     临时绕过手段, 现已改为不加载(保留在盘上备用)。
  4) 关键实测数据(重编驱动 + 打开诊断打印):
       cif a0c2000.cif: DIAG snsr-reset[0]: pin=433 pol=1   <- 设备树解析完全正确
       cif a0c2000.cif: DIAG gpio_request(433) = -16        <- -EBUSY, 引脚被占
     即: **gpio_request 返回 -EBUSY, 而驱动对这一失败是静默 return 0**
     (cif.c 里 `if (gpio_request(...)) return 0;` 连一行报错都不打)。
     复位脚于是从未被设成输出, 传感器一直处于复位态, I2C 完全不 ACK。

7.1 现象与决定性证据
--------------------------------------------------------------------------------
  1) 修好根因①(Oops)之后, 摄像头**依然**起不来, i2c-2 上仍然扫不到 0x37。
  2) 于是写了个板上探测工具 tools/camprobe.c(交叉编译成静态 aarch64 二进制),
     它一次把"引脚复用/复位脚电平/全总线扫描/控制器寄存器"全打出来。
     板上跑 /root/camprobe, 关键输出:
       [2] 传感器复位脚状态
           GPIOC SWPORTC_DR  = 0x00000000   (bit17=0)
           GPIOC SWPORTC_DDR = 0x00000000   (bit17=0, 1=输出)
       [4] 对 i2c-2 的 0x37 用多种方式确认
           quick      -> ret=-1 errno=95(Operation not supported)
           readbyte   -> ret=-1 errno=121(Remote I/O error)
           readword   -> ret=-1 errno=121(Remote I/O error)
  3) 判读:
       a) DDR bit17 = 0 => 这根脚 **从来没被设成输出**, 一直是输入(悬空);
       b) errno=121(EREMOTEIO) 是 I2C 从机不 ACK 的标准错误; errno=95 只是
          DesignWare 控制器不支持 SMBus quick 命令, 属正常;
       c) 也就是说: 传感器被按在复位态, 根本不可能应答。
  4) 直接验证(一行命令就见分晓):
       echo 433 > /sys/class/gpio/export
       echo out > /sys/class/gpio/gpio433/direction
       echo 1   > /sys/class/gpio/gpio433/value
       i2cdetect -y -r 2
     => 第 0x37 列立刻出现 "37"! 再跑 camera-test.sh 直接出图。
  5) 全局号换算: XGPIOC_17 属于 gpiochip2(基址 0x3022000.gpio, 全局 416 起),
     所以 416 + 17 = **433**。

7.2 为什么会这样 (cif 驱动的锅)
--------------------------------------------------------------------------------
  1) 复位脚由 CSI 驱动(cvi_mipi_rx.ko, 源码 osdrv/interdrv/cif/chip/cv181x/cif.c)
     从设备树 "snsr-reset" 取: <&portc 17 GPIO_ACTIVE_LOW>。
  2) 它的 _init_resource() 里:
       link->snsr_rst_pin = of_get_named_gpio_flags(..., "snsr-reset", i, &pol);
       if (link->snsr_rst_pin < 0) break;
       if (gpio_request(link->snsr_rst_pin, "snsr-rst-gpio")) return 0;   // 静默失败
       dev_info(&pdev->dev, "rst_pin = %d, pol = %d\n", ...);
  3) 板上实测: dmesg 里**从来没有** "rst_pin = ..." 这一行 => gpio_request 没成功
     (或根本没走到), 函数直接 return 0, 于是这根脚从未被设成输出。
     旁证: /sys/kernel/debug/gpio 里 gpio-433 一直没有被任何驱动占用;
          只有我们手动 export 之后才出现 "gpio-433 (sysfs) out hi"。
  4) 复位脚卡在 0, 传感器就永远处于复位, I2C 不 ACK —— 这解释了之前所有的怪现象
     (MCLK 明明在跑 clk_cam0=24000000 enable_count=1、引脚复用全对、控制器正常、
      却连一个器件都扫不到)。

7.3 修法(已落地): snsr_rst.ko + 开机先加载
--------------------------------------------------------------------------------
  1) 新增极小模块 tools/snsr_rst.c -> snsr_rst.ko, 只干一件事:
       gpio_request(433, "snsr-rst-fix"); gpio_direction_output(433, 1);
     卸载时拉低并释放。GPIO 号可用参数覆盖: insmod snsr_rst.ko gpio=433 active_low=1
  2) 编译(对着目标内核树, 与修 Oops 时同一套环境):
       make -C /home/chen/kbuild/linux_5.10 \
            O=/home/chen/kbuild/build/sg2002_milkv_duo256m_glibc_arm64_sd \
            ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=<snsr_rst 目录> modules
  3) 装机: /mnt/system/ko/snsr_rst.ko
  4) ★ 必须在 cvi_mipi_rx.ko **之前**加载(否则可能被 cif 抢走, 或在它之后才拉高):
       改 /mnt/system/ko/loadsystemko.sh, 在 cvi_mipi_rx.ko 那行前插一行:
         insmod /mnt/system/ko/snsr_rst.ko
       原文件已备份为 loadsystemko.sh.bak_20260930
  5) 验证(冷启动, 全部实测通过):
       dmesg | grep -c 'Unable to handle kernel|Internal error: Oops'   -> 0
       dmesg | grep snsr_rst                                            -> 已拉高(释放复位)
       cat /sys/kernel/debug/gpio | grep gpio-433                       -> out hi
       i2cdetect -y -r 2                                                -> 出现 37
       /root/camera-diag.sh                                             -> 总判定: 通过
  6) 最终结果: camera-test.sh 完整跑通 ——
       "ViPipe:0,===GC2083 1080P 30fps 10bit LINE Init OK!==="
       "rtsp://127.0.1.1/h264" + "Enter TDL thread / Enter encoder thread"
       人脸检测出结果: "Golden 1464 1024 2327"

7.4 顺手修掉的一个坑: camera-test.sh 被残缺程序遮蔽
--------------------------------------------------------------------------------
  1) 原 /mnt/system/usr/bin/camera-test.sh 里写的是 `sample_vi_fd <cvimodel>`,
     靠 PATH 找程序; 而 /root 下有个 **同名但残缺** 的 23048 字节 sample_vi_fd,
     在 /root 目录里执行时会被优先命中, 只报

  2) 已把 camera-test.sh 改成绝对路径:
       exec /mnt/system/usr/bin/ai/sample_vi_fd /mnt/cvimodel/scrfd_768_432_int8_1x.cvimodel
     原文件备份为 camera-test.sh.bak_20260930。
  3) 真程序是 /mnt/system/usr/bin/ai/sample_vi_fd (155960 字节);
     /root/sample_vi_fd (23048 字节) 不要用。

7.5 最终修法(推荐): 重编 cvi_mipi_rx.ko, 而不是打补丁
--------------------------------------------------------------------------------

       NEWK=/home/chen/kbuild/linux_5.10

       make -C "$NEWK" O="$NEWB" ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
            M="$PWD" -f "$PWD/.kbwrap.mk" modules

  2) 装机并冷启动(板子侧):
       cp -n /mnt/system/ko/cvi_mipi_rx.ko /root/ko_backup_20260930/cvi_mipi_rx.ko.orig
       cp -f /root/cvi_mipi_rx.clean.ko /mnt/system/ko/cvi_mipi_rx.ko

  3) 验收(冷启动实测, 板上已通过):

       lsmod | grep snsr_rst    -> 0 个(不需要了)

         -> "ViPipe:0,===GC2083 1080P 30fps 10bit LINE Init OK!==="
         -> "rtsp://127.0.1.1/h264"
         -> "Enter TDL thread" / "Enter encoder thread"
         -> 人脸检测 "Golden 1464 1024 2327"
  4) 复位脚的正确时序(必须知道, 否则会误判):
       a) 开机后 cif probe: 只 **申请** 引脚, 不拉高 ->
          调试口显示 `gpio-433 (...) in  lo` (input, 低) —— 这是**正常**的;
       b) 跑 camera-test.sh 时, 用户态经 ioctl(实现在 sample_common_vi.c 的

8.1 【本次】camera-test.sh 停在 vi init failed
--------------------------------------------------------------------------------
  1) 现象: 见 2.1 节第 1) 条; 前面必有 "family ID request : receive error"。
  2) 定位: 这句话来自 /mnt/system/usr/lib/libsys.so, 含义就是"I2C 读不到传感器 ID"。
  3) 判据: i2cdetect 扫 i2c-2 看不到 0x37 (见 3.3 节)。
  4) 处理: 走 5.1 节的硬件排查顺序; 一条命令版见 4.1 节的 camera-diag.sh。

8.2 【易误判】/root/sample_vi_fd 报 Failed to get senor infomation from ini file
--------------------------------------------------------------------------------
  1) 现象: 在 /root 下手敲 /root/sample_vi_fd ... , 只打印到
       Failed to get senor infomation from ini file (/mnt/data/sensor_cfg.ini).
     就退出, 退出码 255, 连 MMF Version 都不打印。
     两个参数写法都一样(相对路径 ./sample_vi_fd x.cvimodel, 或绝对路径), 都失败。
  2) 原因: **/root 下这个 23048 字节的 sample_vi_fd 与 /mnt/system/usr/bin/ai/ 下
     那个 155960 字节的, 是两个不同的构建产物**, 这一点用内嵌字符串可以硬证:
       a) /root/sample_vi_fd 调用表里有 SAMPLE_PLAT_VI_INIT / SAMPLE_COMM_SYS_Init /
          SAMPLE_COMM_VPSS_Init, 但**没有 CVI_SYS_Init**;
       b) /mnt/system/usr/bin/ai/sample_vi_fd 有完整的 CVI_SYS_Init / CVI_SYS_IonMmap /
          CVI_SYS_MmapCache / CVI_SYS_RegisterThermalCallback / CVI_SYS_VI_Open 等。
     也就是说: 真程序会先把中间件系统初始化起来(CVI_SYS_Init 建立 ion/内存映射,
     注册温控回调), 再走 VI; 而 /root 那个不做这一步, 于是在读完 ini 之后就报
     "Failed to get senor infomation" 直接返回 —— 它根本走不到摄像头。
  3) 判据(一条命令区分):
       strings /root/sample_vi_fd | grep -c CVI_SYS_Init                  -> 0
       strings /mnt/system/usr/bin/ai/sample_vi_fd | grep -c CVI_SYS_Init -> 有
  4) 处理: 一律用真程序。本文 7.4 节已把 camera-test.sh 改成绝对路径, 所以
     直接跑 camera-test.sh 就是对的:
       cd /root && camera-test.sh
     实测同一条命令下, 真程序立刻出 "===GC2083 1080P 30fps 10bit LINE Init OK!==="。
  5) 注意: 这两个程序输出的 ini 解析段落**逐行一样**, 所以光看那几行分辨不出来,
     必须看后面有没有 "MMF Version" / "GC2083 ... Init OK" 才能判断。

8.3 【易误判】内核刷 "i2c_designware 4010000.i2c: controller timed out"
--------------------------------------------------------------------------------
  1) 现象: dmesg 里每约 1 秒一条, 看起来很像摄像头在反复失败。
  2) 真相: 0x4010000 是 **i2c-1**(GP4/GP5), 不是摄像头的 i2c-2(0x4020000),
     见 1.3 节。所以这条与摄像头无关, 不要拿它当证据。
  3) 补充: 同一时段 dmesg 里成对出现的
       No valid mailbox is available / RTOS_CMDQU_SEND_WAIT timeout
     是 IPCM 邮箱被占满的老问题, 见 2026.9.28-小核-帧率修复与热更.txt 6.1 节, 也与摄像头无关。
  4) 修复 ko 之后多了一个新情况: snsr_i2c 会在每条 I2C 总线上按 0x3D 挂一个桩
     I2C 客户端(cvi_info 里 I2C_BOARD_INFO("sensor_i2c", 0x7b>>1)), 于是
     `i2cdetect -y -r 1` 会卡很久(实测 26 秒才被打断)。所以自检脚本现在**先扫
     i2c-2**(摄像头那条), 并且每条总线都加了 20 秒 timeout。

8.4 ★【重要纠正】"family ID request : receive error" 与摄像头**无关**
--------------------------------------------------------------------------------
  1) 本次排障一开始把这句话当成"摄像头没应答"的证据, 这是**错的**, 特此订正。
  2) 真正的出处: cvi_mpi/modules/sys/src/cvi_thermal.c 第 127 行。
        nl_request_msg.g.cmd = CTRL_CMD_GETFAMILY;      // 通用 netlink 查家族
        ... snprintf(family_name, ..., "thermal_event");
        ... 失败时: fprintf(stderr, "family ID request : receive error\n");
     即: **温控组件**向内核问 "thermal_event" 这个 genl 家族名, 内核没这个家族,
     于是报这句。它跟 I2C、跟传感器 ID 一点关系都没有。
  3) 判据: 该字符串只存在于 libsys.so(以及各 sample 程序), **不在** libsns_full.so
     也不在任何 .ko 里。早期记录里"这句话来自 libsys.so"这一半是对的, 但把它解释成
     "驱动读不到传感器 ID" 是错的。
  4) 教训: 报错字符串要追到**源码文件行号**再下结论。认错了出处, 就会把整条排查方向
